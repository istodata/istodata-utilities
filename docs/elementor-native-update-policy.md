# Native Elementor updates and Kit runtime compatibility

The2026-10-26 product decision supersedes compatibility-based updater blocking and the special pair/override workflow. Native WordPress/vendor checks govern manual, bulk, automatic and ZIP updates. Old pair/override POST endpoints return410; old grants/coordinator cannot install anything. Available updates stay visible. Existing class/screen URLs and harmless updater callback shims remain, while the information screen is read-only. The independent explicit disable_auto_updates setting and Kit metadata Check again behavior remain unchanged.

The central registry retains all accepted exact combinations and separate tested evidence/limits. New support is additive: retain every previously accepted pair/core-only path and its working runtime/API consumers. Withdrawal requires specific evidence and another explicit user decision. Do not widen ranges, drop Pro dependencies or treat evidence alone as a release-owned accepted declaration. Saved keys, durations, controls, IDs and render contracts remain supported.

Sensitive runtime features fail closed individually. Read actual installed headers per site/network request context, respecting local/network activation. Native post-install observation invalidates all cached site contexts after shared file changes and returns the native result unchanged. Inactive Core cannot enable adapters; inactive Pro preserves only the documented core-only static-cache path, while network-active Pro cannot be ignored. Unsupported functions bypass without rewriting settings and recover automatically on accepted versions.

The 2026-10-27 decision supersedes the earlier advice-even-OFF rule: each native Elementor/Pro update row advises about its target plus actual installed counterpart only for active related Kit functions. With all related functions OFF, no Kit update advice appears. Supported/affected labels and a destination needing both updates use only this active subset. Preserve verified advice for an active unaffected function without warnings about inactive functions. Distinguish accepted compatibility, an accepted destination needing both available updates with an unverified intermediate, and unverified/missing target metadata with affected-feature bypass. This is not a whole-site/vendor guarantee. Long evidence belongs in details; one combined runtime warning covers affected active functions. No special update process is required.

Plugins uses the existing `in_plugin_update_message-{plugin}` action. WordPress Updates uses the same evaluator/text via `site_transient_update_plugins`, only during the actual `get_plugin_updates()` call made by `list_plugin_updates()` on the authorized update-core screen. WordPress has no equivalent per-plugin action there; its native `upgrade_notice` field renders after compatibility information. Decorate cloned transient/response objects for display, preserving the vendor notice and all update/package/check fields; direct reads, metadata refresh, installers and cached objects remain untouched. No DOM rewrite, buffer rewrite, extra form, global available-update notice or updater gate is added. Core strips tags from the field, so Updates contains the same escaped advice text without the extra Plugins information link.

Multisite advice explicitly identifies the current site's ID and states that it is not a network-wide assessment. It uses that loaded site's activation/feature/experiment context; it does not reuse a cached Elementor experiments singleton across switched sites or infer other sites' activity. Network updater advice requires network-admin context plus update_plugins/manage_network_plugins. A current site with no active related functions yields no advice even if other sites might use them. Full network aggregation is outside this implementation; review this explicit scope before acceptance.
